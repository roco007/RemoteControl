# Android gesture service

This local Expo module owns motion detection on Android. With background gestures enabled, a `connectedDevice` foreground service keeps the accelerometer and an authenticated Wi-Fi control session available after Home, task dismissal, or screen-off. The persistent notification opens Remote Mac or stops gestures. Android Force Stop stops the service until the user opens the app again; the module does not bypass that action or start itself at boot.

While the activity is visible, detected gestures go to the existing JavaScript client, which owns the foreground Wi-Fi/Bluetooth connection. On a real activity stop, the JavaScript client releases control and the service opens its native Wi-Fi connection after a short handoff delay. The native socket closes before the foreground lifecycle event allows JavaScript to reconnect. Each recognized gesture snapshots its configured list. An admitted foreground list keeps its JavaScript transport while a phone-app launch hides Remote Mac, and blocks new recognition between steps. New gestures are never queued across handoffs or reconnections. Changing the selected Mac or pairing cancels the remaining list. Background Bluetooth is not implemented.

The native connection uses the existing protocol version, origin, server identity, pairing token, capability checks, permissions, sequence numbers and heartbeat. Pairing configuration is encrypted with an app-owned Android Keystore key. Terminal authentication/protocol failures clear the saved Mac credentials through `clearPairing()` while retaining the master setting and phone-app mappings. Independent phone actions remain available offline; reconnect in the app to restore Mac actions. `stop()` still clears the complete configuration for an explicit disconnect. The partial wake lock covers enabled background listening (including phone-only profiles) and an actively running list. It is released while a pending result is unknown, when controls stop, or when the app returns to the foreground. Android battery restrictions and manufacturer process policies can still affect sustained background execution.

`GestureService.configure()` takes the JSON form of `GestureConfiguration` from `index.ts`, including the last observed `controlRevision`. The native master preference is durable and separate from actual `listening` and connection status. `controlEnabled` is null before the first configuration; only then does `configure.enabled` initialize it. Later user changes use `setEnabled(boolean)` or `setBackgroundEnabled(boolean)`. Status also returns `controlRevision` and `controlBackground`; `configure.controlBackground` seeds the initial background preference while `configure.backgroundEligible` reflects current transport eligibility independently of that preference. Later configurations cannot overwrite either authoritative preference. Configurations with a different revision are ignored, preventing an older React render from undoing a widget tap or a newer app switch choice. `onStatus` publishes runtime state and gesture counts; `onGesture` routes foreground actions; `onAppState` coordinates foreground transport lifecycle.

The 2-by-1 **Remote Mac gestures** home-screen widget shows the desired ON/OFF setting and separate listening/connection detail. While a directional action list runs, its whole display shows only **Left**, **Right**, **Left → Straight**, or **Right → Straight** in large centered text. The name comes from the admitted action list, stays through its steps, and restores the normal display when execution finishes or completion becomes unknown. Count gestures keep the normal display. Its immutable explicit PendingIntent reaches a non-exported provider. An ON tap enables background gestures and starts the foreground service directly from the widget interaction when a saved paired Wi-Fi configuration or a phone-app action profile is available. With neither profile, the widget opens the app for setup. `requestPinWidget()` asks a supporting launcher to show its add-widget prompt; true means the request was accepted, not that the user finished adding it. Package replacement refreshes the widget without starting gestures.

Ordinary OFF and **Stop gestures** from the notification retain encrypted pairing, mappings, and settings for the next ON tap. `stop()` is reserved for disconnecting or invalidating pairing: it disables gestures and removes the saved configuration. Every explicit master or background toggle advances the revision. `GestureControlPolicyTest` covers retention, stale configuration rejection, pairing removal, early initialization, and background preference versus Bluetooth eligibility.

`MotionGestureDetector` is pure Kotlin. It uses raw accelerometer readings in g, sensor timestamps in milliseconds, and monotonic `tick()` calls. Plain **Left** and **Right** remain flicks, with acceleration and braking treated as one movement. **Left → Straight** and **Right → Straight** mean tilting the phone to that side and then returning it upright to its starting portrait posture. The tilt action completes only after the return settles; it is not a pair of opposite flicks.

The canonical tilt gesture IDs are `left_straight` and `right_straight`. Loading a saved native configuration moves `left_right` and `right_left` action assignments to those IDs; explicit new assignments win when both exist. Every subsequent encrypted save writes canonical keys. Old IDs are not accepted as runtime gestures or calibration targets. Previous compound calibration marks do not count as training for the new tilt movements; unrelated saved calibration is retained.

Motion calibration records five takes of each selected label: five for one individual movement or thirty-five for all seven. Each recording has a 1.2-second preparation period and a 6.5-second recording window, anchored to the first sensor frame. A foreground-only native collector works without a Mac connection or an enabled gesture master. Every completed capture with sensor data advances the take count, including still or unconventional motion; only actual sensor/read failure requires retry. Save retains all five new generic motion templates per label. New version-3 (`motion_xy`) models use only X/Y and the nearest matching individual example without requiring agreement with the other examples or a predefined flick/tilt/count shape. Generic inactivity detection prevents idle triggers. Targeted retraining preserves other models and legacy settings; the previous profile remains saved until Save succeeds. Profiles are separate from pairing credentials and used by the same detector in foreground and background. Earlier profiles and existing ten-example version-1/version-2 models remain readable without trimming; retraining replaces only the selected labels with five-example version-3 models.

While calibration is active, the service resets pending gestures and blocks sensor listening, foreground gesture events, and background action dispatch. Leaving the app interrupts recording and keeps that guard active. Continue keeps accepted takes and retries only the unfinished capture; Cancel ends the draft. Destroying the React module cancels the session and resets the detector before normal service operation resumes. The widget and service notification reflect the paused state. `onCalibration` emits session ID, monotonic sequence, selected gestures, movement/take progress, and separate saved `calibratedGestures` and `learnedGestures` coverage. New raw captures are saved atomically alongside the learned profile, with bounded full-precision compact arrays and a 2 MiB record limit. Cancel discards the draft. Models and recordings are not sent to the Mac.

`getCalibrationReadings(gesture, draftSessionId)` is a read-only, on-demand bridge call. A null session ID reads saved takes; a matching active session ID reads its completed draft takes without affecting collection. Each take exposes raw XYZ in g, including gravity, with milliseconds relative to its first sensor frame, plus the matching template and metadata when available. Raw captures include the 1.2-second preparation period. Older models without original readings return `raw: null`. The matching view shares `MotionXY.effectiveProfile` with the runtime: it rebuilds older templates from original X/Y readings when available, otherwise projects and rescales their saved 32-point shapes. Original stored models and XYZ readings remain untouched. Responses declare `recognitionAxes: ["x", "y"]` and include effective model version, stored model version, and template provenance (`stored`, `raw_rebuilt`, `projected`, or `draft`). Large reading arrays are excluded from progress events. The UI graphs and compares X/Y, labels Z as ignored in the paginated raw sample table, and explicitly share all takes of the selected label as JSON. It keeps normalized template positions separate from original sensor time and fences stale replies by session, movement, and profile revision.

With the phone upright, X is left/right and Y is up/down. Projection happens before recognition activity, trimming, normalization, matching, and quiet-time checks, including legacy/untrained recognition. A depth-only signal cannot start or extend a gesture. These are phone-relative acceleration axes; heavily pitched or flat poses are not an equivalent upright gesture. Existing timing windows and distance thresholds remain unchanged. Effective conversion runs when configuring a detector or reading calibration, never per sensor frame. Saving selected labels uses the original stored profile so unrelated raw archives remain intact.

Native validation tasks in a prebuilt Android checkout:

```
./gradlew :gesture-service:compileReleaseKotlin :gesture-service:testDebugUnitTest
```

The detector and protocol tests do not establish physical gesture recognition. Device verification must also check the actual notification, enabled sensors, session handoff, task dismissal, and a user-performed gesture.

## App, URL, and command action lists

`mappings` accepts each legacy action string or an ordered array of up to 20 steps. An empty array disables a gesture. Steps use `{type:"system", action}`, `{type:"open_app", target:"mobile"|"server", appId, appName?}`, `{type:"open_url", target:"mobile"|"server", url}`, or `{type:"run_command", command}`. Application IDs, display names, URLs, and commands retain separate fields. Native and JavaScript parsers share the 2048-character app ID, 160-character display name, and 4096-character command/URL limits. URL steps accept absolute HTTP/HTTPS addresses with a valid ASCII or punycode host, reject credentials/whitespace/control characters/backslashes/malformed escapes, and preserve path, query, fragment, and case. Corrupted lists are rejected rather than partly executed.

`listInstalledApps()` uses Android's MAIN/LAUNCHER package query, deduplicates packages, excludes disabled apps and Remote Mac itself, and returns labels and PNG icons. `openMobileApp(appId)` launches the selected package while the activity is visible. Phone-only lists can listen without Mac pairing. `foregroundAllowed` preserves foreground pause/calibration controls for local actions. `preservePairing` allows normal same-host configuration refreshes to retain encrypted Mac credentials without exposing them to JavaScript; false prevents retention after revocation.

Phone URL steps use an HTTP/HTTPS `ACTION_VIEW` intent with the BROWSABLE category and Android's default link handler. The manifest declares both URL schemes for handler visibility. Completion confirms that Android accepted the launch, not that a page loaded. Mac URL steps require the receiver's `open_url` capability and use the same operation lifecycle as other Mac actions.

The service runs one step at a time, waiting for the receiver's correlated completion before sending the next Mac action. Each Mac step gets its own operation ID. Known failures continue to later steps. Unknown results keep the list paused; explicit Resume cancels its unsent remainder. Process loss discards the unsent snapshot, and neither reconnection nor app reopening replays it. `batchPending`, `batchOwner`, `batchIndex`, `batchTotal`, and `batchSummary` expose progress and failures. Command text, URLs, and app IDs are excluded from action logs and durable operation metadata.

Android treats a foreground service as background for [activity launch restrictions](https://developer.android.com/guide/components/activities/secure-bal). A background phone-app or phone-URL step posts a tap-to-open notification and reports that a tap is needed; it does not claim the destination opened. Later steps continue. If notifications are denied or the channel is disabled, the step reports a failure. A notification tap opens the destination directly through an immutable activity PendingIntent. URL notification identifiers use a hash and status text does not contain the URL. Physical notification/launch behavior still needs a newly built APK and device verification.
